# Agents.md

Контекст для Codex/OpenAI-агентов, которые работают с этим проектом из разных учетных записей. Этот файл нужно читать в начале новой сессии вместе с `docs/corporate-ui-guidelines.md`.

## Зачем нужен файл

Проект развивается итерационно, через короткие правки интерфейса. Важна не только конкретная визуальная правка, но и сохранение единой дизайн-системы. Если пользователь просит изменить похожий элемент, задача почти всегда не в локальном переопределении страницы, а в унификации общего компонента и последующем применении его на нужном экране.

Главный принцип: сначала найти существующий эталонный паттерн, затем обновить общий компонент, затем применить его на странице.

Если пользователь не пишет явно "уникально", "только здесь", "исключение", "локально" или другую формулировку исключительности, любую визуальную/поведенческую правку повторяемого UI нужно считать глобальной правкой дизайн-системы. Сначала менять общий компонент и его правила, затем подключать/применять их на нужных страницах. Локальные page-правки допустимы только для раскладки конкретной страницы или явно уникального случая.

Для интерактивных компонентов "переиспользовать компонент" означает переиспользовать весь контракт компонента: HTML-структуру, классы, `data-*` атрибуты, ARIA-состояния, JS-механику, состояния выбора/сброса/поиска и overflow-поведение. Нельзя собрать рядом новый локальный блок, который только внешне похож на компонент или использует часть его классов. Если эталон уже есть, нужно сначала перенести/обобщить его главный компонент и только потом подключать этот же компонент на новой странице.

## Стартовый порядок работы

1. Проверить рабочее дерево:
   - `git status --short`
   - не откатывать чужие изменения;
   - если файл уже изменен, читать его фактическое состояние и работать поверх него.
2. Прочитать контекст:
   - `Agents.md`;
   - `docs/corporate-ui-guidelines.md`;
   - `assets/css/tokens.css`;
   - `assets/css/components.css`;
   - релевантные HTML/CSS/JS страницы.
3. Искать через `rg`, не гадать:
   - где уже есть похожий компонент;
   - какая страница сейчас является эталоном;
   - какие классы и иконки уже используются.
4. Если меняется CSS/JS, проверить query version в HTML (`?v=...`) и поднять ее для затронутого файла.
5. Перед финалом сделать минимум:
   - `rg` по новым классам/атрибутам;
   - синтакс-проверку JS, если доступен `node`;
   - коротко сообщить, если проверка невозможна из-за окружения.

## Модель взаимодействия

Пользователь часто формулирует коротко и уточняет по ходу. Самое свежее уточнение имеет приоритет над предыдущей формулировкой.

Рабочий стиль:

- отвечать и финализировать на русском;
- не спорить с уточнением пользователя, а быстро корректировать направление;
- если пользователь говорит "именно радиус", менять `border-radius`, а не gap/padding/margin;
- если пользователь говорит "в компоненты", правка должна попасть в общий компонент, обычно в `assets/css/components.css`;
- если пользователь говорит "как у вагонов" или указывает существующую страницу, это эталон для переиспользования;
- если пользователь говорит "не готово", обычно проблема в том, что обновлен только локальный блок, а не весь набор компонента и его варианты;
- если пользователь просит "не плодить компоненты", нужно расширять существующий мастер-компонент модификатором или общим селектором, а не создавать новый независимый паттерн.

Когда есть сомнение, сначала проверить текущий код и похожие экраны. Вопрос задавать только если без ответа можно сломать продуктовую логику.

## Компонентная методология

### Приоритеты

1. Токены и правила из `tokens.css` и `docs/corporate-ui-guidelines.md`.
2. Общие компоненты из `assets/css/components.css`.
3. Эталонные реализации на существующих страницах.
4. Локальные page styles только для раскладки конкретной страницы или действительно уникального случая.

### Что считается правильной унификацией

- Вынести повторяемый вид и состояния в общий компонент.
- Зафиксировать варианты компонента: базовый, с иконкой, с текстом, числовая ячейка, action-ячейка, badge-варианты, progress/range.
- Не копировать похожий CSS в page-файл.
- Не создавать новый класс, если существующий компонент можно расширить безопасным модификатором.
- При изменении старого компонента обновить его до актуального эталона, а не обходить старую версию локальной правкой.
- Если запрос не помечен как уникальный/локальный, после компонентной правки проверить все страницы-потребители компонента и поднять cache-busting query там, где изменение должно отразиться.

### Что нельзя делать

- Не вводить случайные `px`, цвета и шрифты вместо токенов.
- Не менять текст, если задача про вариант бейджа/цвет/компонент.
- Не заменять общий компонент старым забытым вариантом.
- Не делать "почти такой же" компонент рядом, если уже есть мастер-компонент.
- Если агент без прямой просьбы создал новый паттерн, вариант компонента, локальную имитацию или промежуточный костыль, и пользователь указывает, что это не нужно, этот код удаляется полностью. Нельзя оставлять его как запасной вариант, считать принятым компонентом или ссылаться на него в следующих правках.
- Не собирать локальную имитацию интерактивного компонента рядом с эталоном. Даже если визуально использованы те же классы, но отличаются `data-*` контракт, JS-логика, tri-state, сброс, поиск, overflow или rollover, это считается самодеятельным дублем и должно быть заменено главным компонентом.
- Не добавлять в drawer/filter-modal новые видимые паттерны, которых нет в эталонном drawer, без прямой просьбы пользователя. Если нужен муляж или статичный вариант, использовать существующие блоки drawer (`dt3-multisearch`, `form-input`, date-field, footer/buttons) и менять только тексты, опции и разрешенные классы варианта.
- Не чинить визуально точечно "на глаз" и не пытаться примерно отрисовать интерфейс, если есть компонент, эталон или внутренний контракт большого класса.
- Не создавать и не подставлять "что-то вроде" компонента по собственной инициативе. Если правило компонента или эталон не найден, остановиться и запросить направление; новое создавать только по прямой просьбе пользователя или после согласованного показа пути.
- Не откатывать изменения пользователя без явной просьбы.

## Текущие договоренности по UI

### Чарты

- `series-*` классы исторически задают сразу `fill`, `stroke` и `background`, чтобы работать с SVG-срезами, линиями, HTML-барами и точками легенды. Перед использованием нужно понимать, какое свойство реально рисует элемент.
- Нельзя вешать `series-*` как цветовую заливку на wrapper бара, если настоящая геометрия рисуется дочерним SVG, `rect/path/line` или `::before/::after`. В таких случаях wrapper должен быть прозрачным, а цвет задается на реальной геометрии или через локальную CSS-переменную компонента.
- Для SVG-чартов `series-*` допустимы на самих `path`, `rect`, `line` и на точках легенды. Если в инспекторе у SVG-элемента виден `background`, он не должен использоваться как часть отрисовки; при сомнении добавить компонентное правило `background: none` для SVG-геометрии.
- Если цвета в чарте выглядят слишком насыщенными, сначала проверить, нет ли двойной заливки: общий `series-* background` на контейнере плюс отдельная заливка SVG/псевдоэлемента. Не лечить это `opacity` всей карточки или `!important`.

### Круговой прогресс

- `payment-progress-ring` считается общим компонентом. В JS его нужно рендерить через `ui.progressRing(...)`, а не собирать локальный SVG на странице.
- Для малых значений прогресса `> 0` и `< 12` бар должен отрисовываться короткой SVG-дугой `path`, а не `circle` со `stroke-dasharray`, иначе штрих визуально залезает в текст процента.
- Размер кольца задается переменной `--payment-progress-ring-size`, толщина линии — `--payment-progress-ring-stroke-width`; SVG-геометрия должна сохранять толщину линии через `vector-effect: non-scaling-stroke`.

### Радиусы

- `space 2` означает `var(--space-2)`.
- Для `dt3-search-scope-trigger`, `ui-dropdown__trigger`, `dt3-multisearch-field`, `shell-search-field` радиус должен быть `var(--space-2)`.
- Для `button-small` primary/secondary квадратные варианты должны использовать радиус `var(--space-2)`.
- Исключение: элементы с явно скругленными окончаниями/pill-формой не переводить в `space 2`.

### Таблицы

Табличный паттерн должен жить в `components.css`.

Базовые классы:

- `table-block` для внешней поверхности таблицы;
- `table-wrap` для прокрутки;
- `data-table` как основной общий table-компонент;
- `analytics-table` может использовать тот же набор правил, если таблица относится к аналитическим экранам.

В таблице должны быть покрыты варианты:

- обычная текстовая ячейка;
- главная текстовая ячейка `table-cell-content` с `strong` и `small`;
- числовая ячейка `data-table__numeric-cell`;
- progress-ячейка `data-table__progress-cell`;
- action-ячейка `data-table__action-cell`;
- header content через `data-table__column-heading`;
- header sort через `data-table__sort`;
- header search через `data-table__search`.

Для progress line использовать общий `scenario-range__track`/`scenario-range__line` через `ui.progress(...)`, а не локальные полоски.

### Скроллы

- Эталон scrollbar — сайдбар: `.app-sidebar .app-nav`.
- Для обычных прокручиваемых областей использовать общий класс `ui-scrollbar` или уже подключенный общий scrollbar-селектор в `assets/css/components.css`.
- Не писать локальные `scrollbar-width`, `scrollbar-color` и `::-webkit-scrollbar*` в новом компоненте, если пользователь явно не просит новый scrollbar-паттерн.
- В фильтрах/dropdown служебная часть (`control`, divider, search) не прокручивается вместе со списком. Скролл должен быть на options-слое (`form-input__options` или общий options-контейнер) и брать внешний вид из общего scrollbar-паттерна.

### Бейджи

- `badge` и варианты `green`, `orange`, `red`, `purple` должны быть общими.
- `badge purple` существует как вариант компонента и используется как на странице вагонов/логистики.
- В таблице "Реестр оборудования" статус `Онлайн` должен оставаться текстом `Онлайн`, но визуально рендериться как `badge purple`, а не `badge green`.
- Не менять слово на "Пёрл"; речь была о пересадке visual tone на purple.

### Кнопки

- `button-small` primary/secondary использовать для обычных компактных действий в шапках.
- `button-smallest-secondary-radius` и `button-smallest-primary-radius` использовать для самых маленьких действий.
- Если нужна кнопка только с иконкой, использовать `button-smallest-secondary-radius button-smallest-secondary-radius--icon typography-button-smallest`.
- Иконки в таких кнопках брать из `assets/icons/financial-interface.svg` или `assets/icons/bnt-sprite.svg`, если символ уже есть.

### Реестр оборудования

Текущие решения по странице `equipment.html` / `assets/js/pages/equipment.js`:

- Таблица обернута в `section.card.table-block > .table-wrap > table.data-table`.
- Колонка паспорта называется `Паспорт`.
- Кнопка паспорта икон-only, класс `button-smallest-secondary-radius button-smallest-secondary-radius--icon typography-button-smallest`, символ `financial-interface.svg#StrokeDoc`.
- Кнопка паспорта центрируется через `data-table__action-cell`.
- В header таблицы:
  - `Оборудование` имеет только поиск;
  - `Категория` имеет поиск;
  - `Локация` имеет две кнопки: сортировка, затем поиск;
  - `Внутр. №`, `Возраст`, `Нагрузка`, `Износ`, `Последнее ТО`, `Следующее ТО`, `Статус` имеют сортировку;
  - `Паспорт` без кнопок.
- Сортировка использует символы `SortDefault`, `SortDescending`, `SortAscending`.
- Поиск в заголовке открывает общий фильтр с нужной областью поиска, а не создает новый локальный поиск.
- Максимальная высота табличной прокрутки задается в общем компоненте `.table-wrap`: `max-height: 832px`.

## Правила для новых правок

Перед тем как писать CSS:

1. Найти существующий класс в `components.css`.
2. Найти эталонный экран, где похожий паттерн уже выглядит правильно.
3. Решить, это:
   - тот же компонент;
   - вариант существующего компонента;
   - действительно новый паттерн.
4. Если это тот же компонент или вариант, править общий компонент.
5. Если это новый паттерн, назвать его так, чтобы он описывал роль, а не текущую страницу.

Перед тем как менять HTML:

1. Проверить, можно ли заменить локальную разметку общим классом.
2. Не оставлять старые пустые контейнеры вроде устаревшего `div.filters`, если логика переехала в общий drawer/popover/filter.
3. Обновить cache-busting query для затронутых CSS/JS.

Перед тем как менять JS:

1. Сохранять существующую модель данных.
2. Не менять текстовые значения ради визуального состояния.
3. Для фильтров/сортировки переиспользовать текущий modal/drawer/filter state.
4. Если у компонента уже есть эталонная JS-механика, использовать ее контракт целиком: те же `data-*` селекторы, функции синхронизации, состояния `is-selected`/`is-indeterminate`, сброс, поиск, overflow и обработчики. Локальные адаптеры допустимы только как тонкая привязка данных страницы к общему компоненту.
5. Если сортировка нужна в таблице, она не должна менять независимые summary/cards, если это не задано явно.

## Чеклист финала

Перед ответом пользователю проверить:

- правка сделана в общем компоненте, если пользователь просил компонент;
- страница применяет общий класс, а не локальный дубль;
- радиусы, отступы, шрифты и размеры взяты из токенов;
- варианты ячеек таблицы покрыты не только визуально, но и классами;
- иконки идут через существующий sprite/symbol;
- версии подключенных CSS/JS подняты;
- не затронуты посторонние файлы намеренно;
- если проверку нельзя выполнить, это честно указано в финальном ответе.
