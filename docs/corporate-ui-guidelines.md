# Corporate UI Guidelines

> Рабочий справочник по визуальной системе, адаптиву и UX для корпоративных интерфейсов.
>
> Этот файл фиксирует правила, подтвержденные текущими референсами проекта. Если конкретное значение здесь не указано, его нельзя додумывать: следует использовать существующий токен/компонент или запросить уточнение.

---

## 1. Источники и приоритет правил

При проектировании использовать следующий приоритет:

1. **Этот справочник и подтвержденные токены проекта** — визуальная система и технические правила.
2. **Существующие компоненты продукта** — если они уже реализуют подтвержденное правило.
3. **UX-паттерны из _Designing Interfaces: Patterns for Effective Interaction Design, 3rd Edition_ (Jenifer Tidwell, Charles Brewer, Aynne Valencia, O’Reilly, 2020)** — руководство по поведению интерфейса и выбору UX-паттернов.
4. Если продуктовая логика или утвержденный макет расходятся с общим UX-паттерном, расхождение нужно обозначить, а не молча заменять продуктовое решение.

Книга используется как UX-руководство, а не как визуальный шаблон. Визуальная реализация всегда должна соответствовать нашей дизайн-системе.

## 2. Базовые UX-принципы

- Проектировать от **цели пользователя**, а не от набора функций.
- Часто используемые действия и важные данные должны быть доступны сразу.
- Сложные задачи разбивать на понятные шаги/секции, не перегружая один экран.
- Интерфейс должен постоянно давать обратную связь о состоянии системы и результате действий.
- Поддерживать **safe exploration**: пользователь должен иметь возможность пробовать, отменять и возвращаться без лишнего риска.
- Поддерживать **spatial memory** и habituation: стабильные элементы не должны без причины менять положение и поведение.
- Для редких/новых задач интерфейс должен помогать и объяснять; для регулярных/экспертных сценариев — не мешать эффективности.
- Не заставлять пользователя принимать решения раньше, чем это действительно необходимо; использовать разумные defaults и progressive disclosure.
- Для Dashboard показывать прежде всего актуальную и actionable-информацию, убирать второстепенное, обеспечивать визуальную иерархию и drill-down в детали.
- Для больших наборов данных использовать понятные списки, таблицы, карточки, фильтры и сортировки; не усложнять визуализацию без необходимости.

## 3. Responsive / Breakpoints

### 3.1. Диапазоны

| Диапазон | Роль | Правило |
|---|---|---|
| `> 1440` | XL | Масштабирование от базового экрана пропорционально `vw` |
| `1200–1440` | Base | Основной диапазон проектирования. Все базовые макеты строятся здесь |
| `960–1199` | Breakpoint | Наследует значения от Base, если нет локального override |
| `640–959` | Mobile | Следующий breakpoint; здесь применяется mobile typography scale |
| `390–639` | Breakpoint | Наследует от `640–959`, если нет локального override |
| `< 390` | XS | Масштабирование пропорционально `vw` от 390 |

### 3.2. Наследование

Главное правило:

> При уменьшении экрана значения наследуются с предыдущего большего breakpoint. Новое значение задается только как явный override.

То есть не нужно дублировать одинаковые правила на каждом breakpoint.

### 3.3. Что масштабируется

При масштабировании выше 1440 и ниже 390 могут пропорционально масштабироваться:

- типографика;
- размеры контентных областей;
- ширины колонок;
- размеры крупных layout-блоков, когда это предусмотрено компоновкой.

### 3.4. Что не масштабируется

Фиксированными остаются:

- линии и strokes;
- border width;
- тени и их offsets/blur/spread;
- базовые spacing-токены `8 / 12 / 24 / 48`;
- grid gutter `24px`;
- крайние grid offsets `12px`.

Пример: линия `1px` остается `1px` на любом экране.

## 4. Grid / Layout

Сетка — это **система пропорций и ритма**, а не требование верстать каждый экран literal CSS Grid на 12 колонок.

Если используется `flex`, карточки, таблицы или иной layout, сетка помогает определить:

- ширины блоков;
- расстояния между блоками;
- общий визуальный ритм;
- кратность размеров.

### 4.1. Базовая сетка 1440 без навигации

| Элемент | Значение на 1440 | Поведение |
|---|---:|---|
| Крайний отступ слева | `12px` | фиксированный |
| Крайний отступ справа | `12px` | фиксированный |
| Рабочая колонка | `94px` | сжимается/растягивается |
| Gap между колонками | `24px` | фиксированный |
| Шаг направляющей | `118px` | производный: `94 + 24` |

`118px` — не отдельная ширина контентной колонки, а шаг центральных направляющих, разделяющих фиксированный gap `24px`.

### 4.2. Сетка с левой навигацией — открыта

Левая навигационная панель: `264px`.

| Элемент | Значение на 1440 |
|---|---:|
| Крайние offsets | `12px` |
| Рабочая колонка | `72px` |
| Gap | `24px` |
| Шаг направляющей | `96px` (`72 + 24`) |

### 4.3. Сетка с левой навигацией — закрыта

Левая навигационная панель: `60px`.

| Элемент | Значение на 1440 |
|---|---:|
| Крайние offsets | `12px` |
| Рабочая колонка | `89px` |
| Gap | `24px` |
| Шаг направляющей | `113px` (`89 + 24`) |

В Figma-референсе для этого варианта также присутствует вспомогательный guide `16 columns (89px)`. Его использовать как визуальную направляющую, а не как обязательное требование к DOM/CSS структуре.

### 4.4. Практическое применение

Если, например, в `flex` нужно разместить 4 карточки:

- сохранить `24px` между соседними карточками;
- заполнить доступную ширину без произвольных зазоров;
- учитывать состояние навигации;
- стараться использовать размеры блоков, кратные `12px`, если это не ухудшает задачу;
- для крупных смысловых групп использовать расстояние `48px`.

## 5. Spacing

Базовая шкала:

`8 → 12 → 24 → 48`

| Токен | Рекомендуемое применение |
|---:|---|
| `8px` | Очень компактные внутренние отступы, расстояния между мелкими элементами |
| `12px` | Вложенные/небольшие карточки, компактные блоки |
| `24px` | Основные карточки, стандартный внутренний padding, стандартный gap |
| `48px` | Разделение крупных смысловых групп/секций |

Правила карточек:

- внутренний базовый padding карточки: `12px` или `24px` в зависимости от размера и вложенности;
- расстояние между карточками/блоками: `24px` или `48px`;
- по возможности сохранять кратность `12px` для крупных размеров и пропорций;
- spacing-токены фиксированные и не масштабируются через `vw`.

## 7. Color system

### 7.1. Общее правило

- Светлый интерфейс использует **Light theme tokens**.
- Темный интерфейс использует **Dark theme tokens**.
- В компонентах использовать **семантические токены**, а не произвольные HEX.
- Альфа-канал является частью токена и не должен заменяться визуально похожим непрозрачным цветом.

## 10. Shadows

Тени не масштабируются через `vw`.

### 10.1. `shadow/raised`

Назначение: raised card elements.

Параметры:

- `0px 2px 4px #385361 @ 5%`
- background blur: `40`

Использовать для поднятых карточек; сочетать с соответствующей raised surface.

### 10.2. `shadow/primary`

Назначение: элементы поверх основного UI — modal, dropdown, flags, inline dialogs, dragged raised cards.

Параметры:

- `0px 2px 4px #385361 @ 20%`

### 10.3. `shadow/elevation`

Назначение: когда контент прокручивается под другим контентом.

Параметры:

- `0px 117px 70px #081F2B @ 3%`
- `0px 52px 52px #081F2B @ 4%`
- `0px 13px 29px #081F2B @ 5%`
- background blur: `40`

## 11. Borders

Border-эффекты фиксированные и не масштабируются.

### 11.1. `Border/XS`

- `0px 1px 1px 0 #447086 @ 8%`
- `0px 0px 0px 1px #447086 @ 8%`
- `0px 0px 1px 0 #03283A @ 10%`

### 11.2. `Border/S`

- `0px 1px 1px 0 #447086 @ 24%`
- `0px 0px 0px 1px #447086 @ 24%`
- `0px 0px 1px 0 #03283A @ 10%`

### 11.3. Focus

- `Border/XS Focus` = базовый `Border/XS` + дополнительная focus-обводка `1px`.
- `Border/S Focus` = базовый `Border/S` + дополнительная focus-обводка `1px`.
- Focus outline всегда остается `1px`.

Точный focus-color token в текущем справочнике отдельно не зафиксирован — не подменять произвольным цветом.

### 11.4. Error

- `Border/Error` использует базовую border-конструкцию + дополнительную error-обводку `1px`.
- Error outline всегда остается `1px`.

Точный error-color token в текущем справочнике отдельно не зафиксирован — использовать утвержденный semantic error token компонента/темы.

## 12. Cards and component composition

- Карточки являются базовым контейнером для группировки связанной информации.
- Для маленьких и вложенных карточек обычно использовать padding `12px`.
- Для основных карточек — `24px`.
- Между соседними карточками — `24px`.
- Между крупными группами карточек — `48px`.
- Если карточки собираются через `flex`, grid-ритм все равно должен сохраняться.
- Не добавлять произвольные spacing-значения, если задачу можно решить через `8 / 12 / 24 / 48`.
- Избегать визуальной перегрузки карточек: secondary metadata и редкие действия должны быть менее заметны, чем основная информация и primary action.

### 12.1. Цвета операционных карточек и причалов

Для карточек используются только следующие парные токены Light/Dark:

| Назначение | Светлая тема | Тёмная тема | Токен |
|---|---|---|---|
| Операционная карточка — положительное, зелёное состояние | `#E2F1E7` | `#18382B` | `operational-card-positive-fill` |
| Операционная карточка — нейтральное, голубое состояние | `#E5F6FF` | `#16384A` | `operational-card-neutral-fill` |
| Причал №1 | `#DDF3EE` | `#173C37` | `pier-card-one-fill` |
| Причал №2 | `#DAE7FD` | `#223754` | `pier-card-two-fill` |
| Причал СВМ | `#FBE8D6` | `#4A3423` | `pier-card-svm-fill` |
| Причал №3 | `#DCEEF2` | `#1B3840` | `pier-card-three-fill` |

- Для операционных карточек с мазутом, нефтью и ДТ применять зелёный или голубой токен по фактическому направлению и состоянию карточки.
- Светлый и тёмный HEX одной строки являются парой одного токена; светлое значение нельзя оставлять в тёмной теме.
- Причал СВМ всегда использует оранжевую пару.

### 12.2. Цвета 3D-визуализации

Палитра 3D-сцены фиксируется отдельно от DOM/UI-токенов. Эти значения применять только для материалов и окружения 3D-визуализации; не использовать их как замену CSS-токенам интерфейса.

| Назначение | Светлая тема | Тёмная тема |
|---|---:|---:|
| sky | `#D9F1FA` | `#092634` |
| fog | `#AEBDC4` | `#092634` |
| ground | `#7F8B80` | `#20404D` |
| asphalt | `#4F565B` | `#48606B` |
| water | `#A9CBD6` | `#204F65` |

При изменении 3D-палитры обновлять пару Light/Dark одновременно и сверять контраст с UI-слоем поверх сцены.

### 12.3. Shared controls, range и поля

Закрепленные правила для общих контролов применять одинаково на всех страницах, где используется этот паттерн.

- `ui-dropdown` и `ui-zoom` считаются общими контролами; локальные страницы могут задавать размеры через CSS-переменные, но не должны менять базовую механику и токены без отдельного согласования.
- `speed-dial-secondary` используется только для вторичных контекстных действий; primary actions должны оставаться видимыми кнопками/ссылками, а trigger обязан поддерживать `aria-haspopup="menu"` и `aria-expanded`.
- `speed-dial-secondary__label` использует `margin-top: 0`; вертикальный ритм trigger задается самим мастер-компонентом, без локальных отрицательных отступов.
- `sign_BTN_smallest` — круглая action/info-кнопка `20px` с SVG `14px`; `sign_BTN_small` — круглая action/info-кнопка `24px` с SVG `16px`. `sign_BTN`, `analytics-kpi__info`, `info-icon-button`, `payment-summary-card__link` остаются совместимыми алиасами. Размер SVG задаётся самим `<svg width height>`, без глобального CSS-переопределения. Расстояние от текста/заголовка до служебной кнопки — `var(--space-1)` (`4px`).
- `CircleCross` и `Expand_2` — библиотечные 16px-символы в `assets/icons/financial-interface.svg`; при использовании через `<use>` сохранять размер конкретного места (`14`, `16`, `20` или `24`), меняя только символ.
- Подтвержденные общие компоненты нельзя клонировать похожей разметкой или локальными CSS-копиями. Для вариантов использовать тот же мастер-компонент с параметрами, атрибутами или согласованным модификатором; новый компонент создавать только для нового паттерна.
- Для всех обычных progress/range/zoom-треков толщина линии — `--progress-bar-track-size: 2px`; заполненная линия/bar использует ту же толщину.
- Scrollbar — исключение из правила `2px`: для WebKit-scrollbar использовать `--progress-bar-track-scroll-size: 4px`, для Firefox допустим `scrollbar-width: thin`.
- Эталон scrollbar — левая навигация сайдбара (`.app-sidebar .app-nav`). Для любых обычных прокручиваемых областей использовать общий класс `.ui-scrollbar` или уже подключенный общий scrollbar-селектор из `components.css`. Не добавлять локальные `scrollbar-width`, `scrollbar-color` и `::-webkit-scrollbar*` рядом с новым компонентом, если не создается отдельный согласованный scrollbar-паттерн.
- В фильтрах и dropdown-меню служебная часть (`control`, divider, search) не должна прокручиваться вместе со списком. Скролл живет на options-слое (`form-input__options` / общий options-контейнер) и наследует общий scrollbar-паттерн из `components.css`.
- Thumb/range-бегунок использует fill `design-elements / illustration / primary` (`--design-elements-illustration-primary`) и border `--progress-bar-thumb-border`.
- В `.field` и поисковых полях placeholder скрывается в focus-состоянии, если назначение поля уже понятно из контекста.

## 13. Navigation states

На desktop учитывать три состояния layout:

1. **Без навигации** — базовая сетка 1440.
2. **Левая навигация открыта** — панель `264px`.
3. **Левая навигация закрыта** — панель `60px`.

Справа может появляться дополнительная контекстная навигация. Ее размеры, состояния и поведение пока не зафиксированы; до появления подтвержденного компонента их нельзя додумывать или переносить с левой панели.

Переключение состояния навигации не должно ломать визуальный ритм, spacing и приоритет контента.

## 14. Implementation rules

### 14.1. Tokens first

Не использовать случайные значения в компонентах, если они уже описаны токенами:

- typography;
- color;
- spacing;
- border;
- shadow;
- responsive rules.

### 14.2. Inheritance first

На меньшем breakpoint сначала наследовать значение предыдущего большего breakpoint. Добавлять override только при реальной необходимости.

### 14.3. Fixed vs scalable

Перед использованием `vw`, `clamp()` или другой fluid-формулы определить, относится ли величина к:

- **scalable content/layout** — может масштабироваться;
- **fixed rhythm/detail** — остается фиксированной.

Не масштабировать strokes, borders, shadows и spacing-токены.

### 14.4. Accessibility and interaction

- Все интерактивные элементы должны иметь понятный focus state.
- Не полагаться только на hover для критичных действий.
- Состояния success/error/warning/neutral должны выражаться семантическими токенами и, где необходимо, текстом/иконкой, а не только цветом.
- Поддерживать предсказуемую keyboard navigation там, где интерфейс предполагает интенсивную работу с данными.

## 15. UX checklist для нового экрана

Перед завершением экрана проверить:

- [ ] Какая главная пользовательская цель на этом экране?
- [ ] Primary action понятен без чтения всей страницы?
- [ ] Часто используемые действия видимы сразу?
- [ ] Второстепенное не конкурирует с главным?
- [ ] Сложная задача разделена на понятные части?
- [ ] Есть понятная обратная связь о состоянии системы?
- [ ] Пользователь может безопасно отменить/изменить решение?
- [ ] Положение основных элементов стабильно и предсказуемо?
- [ ] Использованы токены, а не случайные HEX/px?
- [ ] Spacing соответствует шкале `8 / 12 / 24 / 48`?
- [ ] Cards используют `12/24px` padding и `24/48px` gaps?
- [ ] Учитывается состояние навигации?
- [ ] Адаптив следует inheritance-правилу?
- [ ] На `640–959` применена mobile typography scale?
- [ ] Borders и shadows не масштабируются?
- [ ] Light/Dark тема использует соответствующие semantic tokens?

## 16. Не додумывать

До отдельного подтверждения не вводить новые значения для:

- focus outline color token;
- error outline color token, если конкретный компонент не задает его семантически;
- неизвестных/неподтвержденных palette hex значений;
- дополнительных breakpoint-правил;
- произвольных spacing значений вне базовой шкалы;
- альтернативных typography weights или line-height.

Если макет требует нового значения — сначала проверить существующий токен/паттерн, затем согласовать новый.
